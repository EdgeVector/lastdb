# Blind write path: ack from memory with no read first

Status (2026-10-13): design for Tom's review. Nothing here is built. It follows
`docs/lastdb-warm-set-design.md` (the warm set and the write queue) and changes
its write path. Made by four readers who listed every read on the ack path, one
designer, two skeptics (26 problems found, 24 changed the design, one was not
real) and a revision pass. The agents read the code at commit f7369af0 and ran
nothing. Claims of the form "verified" were checked in code by an agent, not by
a bar. Read the code before you rely on one.

Rules from Tom that bind this design (2026-10-12): a write must not have to read
first; apply to local memory, ack, then the background work writes the log and
the store; a protein write is a separate write to a different key; stale
siblings are fine; a crash between the ack and the sibling writes is fine; order
and conflicts between sibling writes do not matter; batching of sibling reads
and writes should be nice; org (instance prefix) problems are a separate issue.
Earlier rules still bind: a read after an ack of the origin key sees the write;
a purge never drops an unflushed record; the mutation log keeps ack order for
multi-device cloud sync; no tests are written.

Measured today (fresh synthetic home): a write-mode ack is 6 to 9 ms in the node;
a Brain Put pays 107 to 328 ms of protein sibling reads before the ack on real
data (papercuts `papercut-fold-serial-molprot-reads-on-write-20261008` and
`papercut-fold-protein-sibling-write-serial-read-burst-20261008`); the mean
molecule gate hold was 3.1 s on 2026-08-17.

One finding is free: the idempotency read `idem:{content_hash}` never matches a
request write, because the content hash includes the fresh stamp. Dropping it
changes nothing (verified by reading the code, not measured).


## Answer

A plain create or update stamps each mutation, writes atoms and tips to memory, and acks with no store read. The lane then reads the durable tip in one batch, keeps the winner by clock, closes the old atom edge, and writes the store. After the ack, a worker writes each protein sibling as its own tip at its own key with the origin atom and clock, and a full queue sends the request to the current path. Compare-and-set, must_exist, record-envelope schemas, org homes, synchronous requests, replay, and delete (until stage 6) keep a read before the ack. Of the 26 skeptic problems, 24 changed the design and one was not real, and stage 3 now waits for five gates (listed in the staged plan).

## The blind write, step by step

BLIND TEST. The code runs it in memory for the whole request. Every group must pass, or the whole request takes the current path. [B8] A group passes when all of these hold. The origin is Request. Every mutation has authored_locally (a new flag, set at cloud_entry.rs:71-98 before the stamp, outside content_hash, serde skip, so a client cannot set it) and no provenance. The verb is Create or Update. There is no expected, must_exist, aggregate_set or synchronous flag. [B15] There is no storage prefix, no scoped schema and no record molecule. LASTDB_WRITE_DEDUPE and tip history are off. No written slot has a key tombstone overlay without a pending barrier order key in memory. [A6] Until stage 4 the schema has no protein binding. From stage 4 the request also holds a sibling permit. [B9] An aggregate target in the catalog does not fail the test. It only keeps one batch read.

1. Throttle. If a lane that the request names holds more than the soft mark, wait until the lane falls below the mark, up to a bound. Then the outer capture scope reserves the capture permit (it does this today). Reserve the author clock slot and, from stage 4, the sibling permit. All are bounded memory queues. [B4, B9]
2. Stamp. Fold in the highest stamp that the graph has loaded (one atomic read) with observe_remote. [A3] Then give each local mutation its own counter, in batch order. Sign each mutation. A later mutation of the same request now wins on every device. [A2] The pair is above every pair this node observed. No tip is read.
3. Encode the log envelope from the request and the stamp. The capture worker writes it after the ack.
4. Make the ids. Atom id = SHA-256 of schema name and content (atom/atom_def.rs:59-70). The molecule id comes from the schema field (variant/write.rs:159-173). The tip key is the molecule id plus the hash and range of the request key value.
5. Prepare with no read. Take the schema from memory, once. Take the key bundles from the cache. Build the atoms and the key values. Reserve the lane slot and the defer bytes NOW, before any publish. [B3] Skip the idempotency read, the restore, the sibling fold, the share-rule read and the revision snapshot.
6. Lock. Take the slot locks for the origin slots, sorted. Then take lock_tip_publications for the written tip keys. No store read runs while they are held. [A6]
7. Check in memory. Look in the pending delete barrier map. A barrier that wins gets the current error. If the overlay shows a tombstone and no barrier order key is in memory, release the locks and run the current path with the same stamps. Nothing is published yet, and the lane reservation returns on drop. [A6]
8. Seed. seed_resident_subset builds a TAIL shell (from_write_records, version 0) for every written field. It copies each graph tip that exists, with stamp, device, mutation id and key metadata. If a field already holds a catalog molecule, it overlays the graph tips onto that molecule. Keys that are not in the graph stay empty. An empty with_uuid molecule is not a tail, and it would take the exclusive molecule commit lock in the lane. [B7, A7]
9. Write the shell. write_mutation puts the new tip into the shell. The setter keeps the highest stamp key for each slot, also inside one batch. A same atom with a higher key replaces the whole entry (stamp, device, mutation id). [A4, B10] A setter that loses returns unchanged, and the caller then skips the key metadata. [A5]
10. Publish. Write the atoms, then the tips, to the graph as dirty records. Each bump returns (predecessor, target) in the same slot lock section; the first predecessor and the last target for a slot make the ticket. [B13] Clear a key tombstone only for a tip that won. The purge skips dirty records.
11. Mark the log commit as published (mark_logical_commit_published). Fill the lane envelope that step 5 reserved. Put one sibling request in the worker queue with the permit from step 1. None of this can fail. Release the locks.
12. Ack. The reply holds the mutation ids, the counts from the verbs, and durability Queued.

After the change this path has no store read. Two reads can remain: a cold key bundle at first use, and the aggregate guard batch when the catalog holds an aggregate target.

## Reads that stay on the ack path

- Compare-and-set head (CAS). Where: cas_preconditions.rs:18-31 and cas_current_state.rs:23-78. Why it stays: the verb compares the new write with the current value, so a blind write is wrong. Change: answer from the graph first, read all heads of the request with one get_items, and restore only the CAS field. KEEP the per-attempt recheck (create_update_batch/apply_gate.rs:101-137) and the slot revision compare. The CAS lock stops only other CAS writers. A plain writer can move the head between the first check and the prepare. A blind writer bumps the slot revision at publish, so the compare still catches it. [B1]
- must_exist update gate. Where: cas_preconditions.rs:66-172 and cas_current_state.rs:185-288. Why it stays: the contract refuses an absent key. Change: probe the written fields from the graph first, then read ALL other schema fields with one get_items. Today the sweep reads field after field (up to 24 for BoardCards, a guess). Do not probe one key field only. A Hash, Range or Single schema writes no key-field atom, and old HashRange rows lack one. The code comment (cas_preconditions.rs:55-65) names this refuse-or-heal case. [B2]
- Record-envelope fold. Where: write/schema_delta_helpers.rs:19-24 into record_molecule/dual_write.rs:21-58. Why it stays: the atom id of a compacted record depends on the merged document, and readers prefer a complete envelope over field tips. It runs only for schemas that have a record molecule. Change: batch the record-tip reads. Decision 10 picks the rework.
- Aggregate guard read. Where: aggregate/write_set.rs:84-119 and 158-198. Change 1, in memory: if no schema in the catalog declares both aggregate fields (AGGREGATE_VALID_FIELD and AGGREGATE_GUARD_TOKEN_FIELD), no guard can exist, and the whole path is skipped. This holds for the schema of the two bars. A flag refreshes with the schema state cache. Change 2: when a target schema exists, every Hash or HashRange write reads its guard, so read all candidates with one get_items (today one read for each mutation, one after the other). The lock aggregate_guard_lock stays. There is NO negative cache: a guard from replay, repair, or a crash would be missed, and the summary would stay valid. This read is on every such write, not only at first use. [B5, A8]
- Key bundle, first use of a molecule in a process. Where: write/molecule_keys.rs:5-36 and molecule_key_store.rs:111-143. Why it stays: without the bundle the storage hash of the atom partition is wrong. Production passes a wrap key (factory/local/boot_wiring.rs:46-53), so the bundle is real on the primary. A cached bundle costs no read. First use costs two reads. Change: warm the bundles at schema load, and read cold ones with one get_items (today a loop, molecule_key_store.rs:266-271). [B17 is not real]
- Replay and request-path imports (data share with provenance). Where: write/replay.rs and WriteOrigin::Replay. Why they stay: they carry a foreign clock and need the compare with the stored tip. Replay runs in the background and has no user ack. Keep the current path.
- Org homes (storage prefix set). Org is a separate issue. Keep the current path, including the catalog read in write/cloud_entry.rs:13-39. The blind test excludes them.
- Delete until stage 6. The protein member expansion (write/batch_inner.rs:21-23, cas.rs:267-294), the reverse-membership expansion (write/erasure.rs:88-163) and the target tip read (write/delete_winners.rs:15-70) read the old row, because the sibling key comes from the old field values. These reads move to the lane in stage 6.
- Loud erasures: Purge and Delete with must_exist. The reply is the answer (target absent), so the ack waits for the lane. They are outside the blind rule.
- Synchronous requests (synchronous true). The receipt says Durable. A sibling write in the worker would not be part of that receipt, so these requests keep the current path with siblings inline. [B15]
- A written key that has a delete overlay but no pending barrier order key in memory. The memory check cannot compare the stamp, so the request takes the current path. This is rare: the overlay lives only until the purge job ends. [A6]
- A mixed request. If any group fails the blind test, the whole request takes the current path. The apply gate is one loop over all groups, and its barrier batch, revision compare and retry loop cover every group. Per-group handling is a later option. [B8]

## Reads removed from the ack path

- Idempotency read idem:{content_hash}, one for each mutation, one after the other (cas_idempotency.rs:13-70, create_update_batch.rs:75-77). The hash includes the fresh stamp (mutation.rs content_hash adds imported_written_at and logical_counter), and the stamp (cloud_entry.rs:78) runs before the filter. So the read always misses for a request write. Verified by reading the code, not measured. Replacement: none for request origin. The lane keeps its idem write (decision 13). Replay keeps the read.
- Old-tip restore for every changed key (restore_missing_molecules, molecules/restore.rs:18-57, called at write/schema_delta.rs:88-97). A cold field costs one header read and 4 to 6 reads for each key. BoardCards has about 24 fields (a guess from the code). Replacement: a tail shell that overlays graph tips (memory), and the durable compare in the lane.
- Protein metadata: the molprot batch, then the protein batch (molecules/protein_batch.rs:70-92). Replacement: the in-memory protein directory in the worker. A cold directory costs the same two batch reads, off the ack path.
- Protein sibling heads: header, tip, generation pointer and delete barrier for each sibling slot, one after the other (protein/ops/batch.rs:83-108, protein/ops/tip.rs:23-37). This is the 107-328 ms that Tom measured on a Brain Put. Replacement: none. The worker writes a blind tip with the origin clock. The lane compare decides.
- Durable delete-barrier batch under the slot locks (create_update_batch/apply_gate.rs:247-299). It adds to the gate hold time. Replacement: the pending barrier map (atom_store/delete_barriers.rs:46-97) plus the overlay. The tip publication locks (lock_tip_publications) STAY, because they order a Put against a Delete on one key. The lane keeps the durable barrier check (items.rs:14-70). [A6]
- Share-rule namespace scan on every personal write (write/schema_delta_helpers.rs:29-48, sharing/store.rs:11-31). Replacement: the lane reads the rules once for each lane batch, off the ack path. There is no memory copy, because rules enter the namespace by snapshot restore and cloud purge or adoption code (sync/engine/cloud_purge_shares.rs:25, cloud_share_refresh/stage.rs:124), not only by the API. A rule that changes between the ack and the lane run only changes the share fan-out of that write. [B12, A8]
- Peer record-protein bind on a write that has a record-molecule field (molecules/apply.rs:206-229). It clones every schema and does 3 reads for each peer. Replacement: step 0 of the worker, memoized.
- Header read mh: to carry the version (db_operations/atom_store/molecules/load.rs:226-274). Replacement: the lane reads mh: in the same get_items as the durable tips and writes durable version plus the changes in the shell. Only reports read this version (verified: the only reads are items.rs:185, generation_activation.rs:140, delete.rs:247 and apply.rs:177, all of which write it back).
- Slot revision snapshot, revalidation and the retry loop of up to 64 tries (create_update_batch/apply_gate.rs:39-65 and 151-174), for a request whose groups are all blind. The loop is memory only, but each retry repeats every sibling read. Nothing was read, so nothing can go stale.
- Per-molecule write dedupe (LASTDB_WRITE_DEDUPE, off by default; dedupe.rs:86-163). A group with dedupe on takes the current path.
- Schema clones: about 8 for each request, and two full state-map clones (memory, not a store read). Load each schema once and pass it down. Use get_schema_state_cached (schema/core/state.rs:25).
- Aggregate guard read, when the catalog has no aggregate target schema (see the list of reads that stay).

## What the lane does after the ack

The lane is one FIFO for each schema (molecules/persist/*). The capture worker, not the lane, writes the mutation log. The lane runs with capture off. NEW marks a change from this design.

1. Wait for the author clock barrier and the slot persist turn (lane_writer.rs:97-130). No change.
2. NEW. Read the share rules once for each lane batch and pick the share prefixes here. This read left the ack path. [B12]
3. Write the atoms (deferred_job.rs, store_deferred_atoms). No change.
4. Write the molecules (store_molecules_changed_keys, changed_keys.rs). The code already reads the delete barriers and the durable tips, one batch each, and keeps the tip with the highest stamp (items.rs:14-70). NEW: add the mh: header key to the durable-tip get_items. NEW: for each accepted slot, write an inactive tip edge for the durable tip when its atom or its stamp differs from the incoming tip. Today only the tips that the ack path read could produce this edge (atom_ref_edges/edge_keys.rs:334-349). Without it, a cold-key update leaves the old atom with a live edge, and the atom is never a reclaim candidate. NEW: write header version = durable version + changes in the shell. NEW: return the dropped slots, each as API-form (molecule, hash, range), carried from changed_key_store_items. The storage key cannot map back to the API form when the key codec blinds the hash. [B11] Write all items in one batch.
5. NEW, loser rule. After the dirty clear, call try_evict_tip for each dropped slot. It refuses a dirty slot or a slot with a newer revision. The next read loads the durable winner. Then feed the winner stamp to the clock (observe_remote) and count lane_dropped_losers. The clock then moves above the winner, so the next write wins. [A3]
6. History link, only when tip history is on (default off). Set prev_tip_id and write the tv: node from the same durable tip entry. A later option is WriteAck.previous (vendor/laststore/src/store/pins.rs:39,70-75). batch_mutate drops that value today (storage/laststore/logical_main.rs:355), and it is ciphertext. So the option needs a new return type and a decrypt step.
7. Schema row and reload (deferred_job.rs:124-175). No change. A later card can write the row only when a binding is new.
8. Side records: idempotency write (kept), retention, Search batch, share fan-out. No change.
9. Complete the persist turn and clear the dirty marks. No change. NEW (stage 2b): then signal the stored barrier of the request. A quarantined or failed envelope drops the barrier. The capture worker then goes on, and the gauge log_ahead_of_store counts it. [A1]

Batch: step 4 is one read batch and one write batch for the whole envelope. The lane takes the shared append lock for a tail shell and the exclusive commit lock for any other molecule (changed_keys.rs:121-135 and 222-262), so step 8 of the ack path always builds a tail. [B7]

Limit, verified: the lane runs the envelopes of one dequeued batch one after the other (lane_writer.rs:41-82). group_commit_max (16) batches the dequeue only. There is no shared fsync, so the drain stays at about 7 each second for each schema.

## Protein siblings as separate background writes

RULE. A sibling is a separate write: its own key, its own slot lock, its own lane job, its own publish. It is not a separate stamp. It carries the origin atom id and the origin clock. Each peer builds the sibling from the origin envelope with that clock (molecules/apply.rs:375-393). A new stamp would split the devices. A sibling tip never enters the mutation log.

TRIGGER. finalize_prepared_schema_delta (write/schema_delta.rs:248) builds one SiblingRequest for each origin write. It sends it with a permit that the request reserved at admission, so the send cannot fail. The request holds: the origin lane key; for each written field the entry molecule id, layout, atom id, origin clock and key metadata; only the key field values that the members name (apply.rs:363-370 clones every string value today); an origin_stored flag that the lane sets when the origin envelope succeeds; a PendingTask. It lists only fields that won in the shell. It reads nothing.

NO SILENT DROP. If no permit is free at admission (queue capacity about 1024, a guess), the request takes the current path with siblings inline. Under load the sibling work therefore never vanishes. The worker never drops a request. If the lane reserve fails, the worker keeps the request and tries again after a short wait. The permits bound the memory. Delete siblings (stage 6) follow the same rule. [B9]

WORKER (one task, new file molecules/sibling_worker.rs). Drain up to K requests or 5 ms (guess). Group the drain by origin lane key. Then, for each group:
0. Bind the peer record protein (apply.rs:206-229), memoized, only when the directory lacks the record molecule.
1. Look up the directory in memory. For cold molecules, send one protein_of_molecules_in_scope and one protein_get_many_in_scope for the whole drain (protein/ops/batch.rs:10-49). The directory maps a molecule to an Arc<Protein>. It is safe to hold, because members only grow (protein/ops.rs:59-123).
2. Plan. For each field and non-entry member, tip_coords_from_fields gives the hash and range. Build the thin tip from the origin atom and clock. Skip the slots that the origin wrote directly (apply.rs:329-343). Skip a member whose key value is absent, as today.
3. Read the cold key bundles of the sibling molecules with one get_items.
4. RESERVE one lane slot on the origin lane FIRST. The current code reserves before it publishes (schema_delta.rs:115-120: no await between apply and the lane fill). If the reserve fails, go to the retry rule above. [B3]
5. Lock the sibling slots in sorted order, then lock_tip_publications for the sibling tip keys. Check the pending barrier map. Build a tail shell from the graph tips (same seed function as the origin path). The setter keeps the highest stamp key. Publish dirty with the one-section bump. Fill the reserved slot with ONE job for the whole group. There is no await between the publish and the fill.
6. For each sibling key that won, append a change event through ChangeFeedStore::append (db_operations/change_feed.rs:73), with the origin mutation id and operation label. The host emits one event for the origin key only (lastdb_node exec/query_mutation_routes.rs:195-216 and 525-545). A watcher of the sibling layout would otherwise see no event. [B14]

LANE STAGE. The job reuses the Write job type with a sibling_only flag: no atoms, no modified fields, no schema row, no side records. This avoids new match arms in lane_writer.rs and quarantine_records.rs. The lane checks origin_stored. If it is false (the origin envelope was quarantined), the lane quarantines the sibling job in the same way: it writes the quarantine record and releases the slot turns, and the dirty pins stay. Otherwise it runs one store_molecules_changed_keys_batch (changed_keys.rs:186-290) with the same durable compare, edge and header rules as the origin. It runs with capture off and is never logged. [B3]

HOW THIS MEETS TOM'S RULES. No old read. Stale siblings are allowed. A crash between the ack and the sibling write is allowed. Order and conflict between sibling writes do not matter, because every write names the same atom with the same clock. A repeat or a reorder changes nothing (the merge rule, stage 2a, keeps the highest key). Batch: one directory pair, one bundle batch, one lock pass and one envelope for each drain and each lane. Org is excluded: a scoped schema keeps the current inline fold (molecules/scoped_gate.rs).

RETRY. A client retry of an acked write has a new stamp, so the idempotency read cannot match it. It makes a second write and derives the siblings again. A retry therefore repairs a lost sibling. [B16]

DELETE (stage 6). The sibling key needs the old row. Under the gate, copy the peer key atom ids from graph tips before the tombstone (memory). In stage 0 of the lane job, read the rest in one unfiltered batch before the erase. Then queue each sibling Delete as its own write with the origin delete clock.

## Stamps and cloud sync

STAMP. prepare_mutation_author_clocks (author_clock.rs:225-298) reads only the clock state in memory, the wall time and the signer key. A write needs no old tip to get its stamp. Every request mutation gets a stamp (cloud_entry.rs:78), so a request write takes the imported-write branch of the setter. The assert at apply.rs:75 never runs for it (verified).

EACH MUTATION OWN COUNTER (A2). Today one request gets one pair, and the random mutation uuid breaks the tie (author_clock.rs:270-295, verified). A request with Create K then Delete K keeps the Put about half the time. Fix: advance the local clock once for each local mutation, in batch order. The signature already covers the counter. The durable high-water is the state after the last advance. A later mutation wins on every device. The receipt revision becomes the last counter of the batch (decision 5). A single-mutation request does not change.

CLOCK CATCH-UP (A3). The stamp comes before any read, so a cold key can hold a higher durable stamp. Verified: only replay and boot feed the clock (observe_remote has no other caller). Three feeds close this. (a) The lane loser rule feeds the winner stamp. (b) The graph keeps the highest stamp that it loaded or rehydrated, and prepare folds it in with one atomic read. (c) A physical snapshot restore feeds the highest stamp of the snapshot (separate card, decision 3). The first write after a restore to a key with a higher durable stamp can still lose. That is last-writer-wins, as with a second device.

LOG, FOLLOWS STORE (A1, stage 2b, decision 1). Verified in this tree: the capture worker stages the marker and appends the log entry with no wait for the lane (sync/capture/write_path/logical_intent.rs:12-52). The entry keeps the bodies inline (sync/log.rs:285-293). The steady-state download skips this device's own entries (transfer/s3_io/download.rs:56-65). So after a crash the log can hold a write that the origin lost, and the origin never gets it back. Fix: the capture job waits for a stored barrier, in queue order, before it stages the marker. The barrier resolves when the origin lane envelope of the request completes. The queue is still one FIFO in ack order, so log order equals ack order. Cost: the cloud copy lags by the lane lag, and the capture queue (capacity 1024, admission limit 100 ms, write_path.rs:44-45) now depends on lane depth. A dropped barrier (quarantine) lets capture go on, with a gauge.

LOG ORDER. The log holds one MutationEnvelope for each request mutation, from the request and the stamp (cloud_entry.rs:100). It holds no old value. The capture job is submitted after the commit future returns (logical_commit_finish.rs:73-113). The blind path adds no await between the publish and the submit. Tips, atoms, headers and siblings are never logged (logical_commit.rs:32-48). A failed log append is a known gap (stage D of the warm-set design). This design does not change it.

WINNER ON EVERY DEVICE. The key is (written_at, logical_counter, device_id, mutation_uuid, atom_uuid). The highest key wins (atom/mod.rs:63-90). A peer verifies the signature and runs the full pipeline with the origin clock. It builds its own siblings from its own protein membership. Replay keeps the current path.

ONE MERGE RULE (A4, B10, stage 2a, decision 2). Today two sites keep the OLD stamp for the same atom: the setter (molecule_hash_range/ops.rs:309) and the molecule merge (merge.rs:49-52). Two sites already use the NEW rule: the lane (items.rs:28-40) and physical replay (sync/engine/replay/records.rs:136-146). So memory and disk disagree today. The blind path would make the winner depend on whether a key is in the graph: a warm key keeps stamp s1, a cold key installs s2. Rule for every setter and merge: compare the full key first. If the incoming key is higher, replace the WHOLE entry (written_at, counter, device, mutation id, signature fields), keep prev_tip_id, push the old tip to pending_replaced_tips so the old edge closes, and do not bump the version. This ships on all paths and is a hard gate for stage 3.

OTHER RULES. 1. Sibling tips never get a new stamp and never enter the log. 2. Two writes to one slot in one batch now have different counters, so the shell setter applies the higher key. 3. A losing setter changes nothing, including key metadata (A5).

## What the graph and the slot revisions become

GRAPH. The graph (ResidentGraph) stays the one memory buffer for unflushed writes. It holds dirty atoms and tips. apply_tip stays an unconditional overwrite. The compare happens just before it, in the shell, under the slot lock. The graph gains three small things: a bump that returns (predecessor, target); the highest stamp that it loaded (an atomic); and nothing else. The lane uses the existing try_evict_tip (resident/graph/purge.rs:110) for a dropped loser. In the warm-set plan the graph shrinks to the write queue. This design does not depend on that step.

SLOT REVISIONS AND TICKETS (B13, stage 2d). The counter and the ticket (predecessor, target) stay. They order the lane: wait_for_persist_turn and complete_persist_turn use them. Verified: apply_gate_transaction reads the predecessor, publishes, then reads the target as three steps (molecules/apply_gate.rs:300-360). A clean eviction (try_evict_tip, purge_tip) can remove the slot between them. Then the new slot restarts at 1, the target is below the predecessor, and the ticket is lost. The fast ack makes writes to one hot key more frequent, so the window matters more. Fix: bump_resident_revision (resident/graph/slots.rs:142) returns (old, new) inside its lock section. The gate keeps the first old and the last new for each slot. This is the slot protocol of the warm-set design (docs/lastdb-warm-set-design.md, SLOT PROTOCOL) in its smallest form, and it is a prerequisite of stage 3.

BLIND GROUPS. For a request whose groups are all blind there is no PreparedSlotRevision snapshot, no prepared_revisions_match, no reseed_stale_deltas and no 64-try loop. The slot revision still bumps at every publish, so a CAS group that runs at the same time still sees the move.

APPLY GATE. It becomes a short memory section: sorted slot locks, then tip publication locks, then the pending barrier map and overlay check, then seed, then publish, then tickets, then the log mark, then the lane fill, then unlock. No storage await runs inside. This removes the durable barrier read under the locks. The sibling slots leave the origin gate. The current gate stays for CAS, imports, replay and any request with a non-blind group.

DELETE BARRIERS AND OVERLAY (A6). The pending barrier now stays in the map until clear_purge_overlays, not until the barrier reaches disk (change the clear point from purge/converge_steps.rs:118-127). A Put whose stamp is below a flushed barrier cannot then pass the memory check while the overlay still shows the key as deleted. The lane keeps the durable check for all older barriers.

WARM SET. The ack path does not touch the warm set. The warm set keeps exact used records with a budget of 10000 records. It gets a record only from a read fetch or from a lane store write after the flush. A blind write adds no record to it at the ack. A burst of writes cannot push hot records out. Dirty tips and atoms stay in the graph until the flush. The purge skips dirty records. The protein directory is catalog metadata and sits outside the budget (decision 14).

## What changes for clients

- Sibling layouts become stale-tolerant. A read of a sibling key right after the ack can return the old record. No bound is promised. A lag gauge reports it. Guess: 1-10 ms with a warm directory, more with a cold one. When the sibling queue is full, the request takes the current path and the siblings are exact at the ack.
- Reply counts. created and updated still count the verbs that the caller sent (create_update_batch.rs:306-317; verified). no_op is 0 for request writes. It was 0 in practice before, because the idempotency key includes the fresh stamp. State in the API document that no_op is for replay only.
- Idempotency. A client retry of an acked write makes a second write with a new stamp and a second log entry. This is true today, because the read never matched. A retry also repairs a lost sibling. [B16]
- Errors move. A protein fold error no longer fails the user write after stage 4. A memory barrier still gives the ack-time error 'a newer Delete won this key'. A durable barrier makes the lane drop the tip and purge it, and the read then shows the winner.
- An acked write can lose to a higher stamp after the ack. This happens for a cold key whose durable stamp is above the new stamp, for example after a snapshot restore with a clock that runs ahead. The read shows the new value until the lane runs, then the winner. The lane counts it and moves the clock above the winner. Today the same write is hidden from the start. [A3]
- Same-request order. Two mutations to one key in one request now resolve in batch order on every device (Create then Delete ends deleted). receipt.revision becomes the last counter of the batch. Before, all mutations of a request shared one counter and a random id broke the tie. [A2]
- An identical rewrite refreshes the tip stamp on every path. Today the memory setter keeps the old stamp and the lane writes the new one. The cost is one active edge and one inactive edge in the lane. [A4]
- The mh: header version no longer counts the writes. It was already not monotonic, because the resident seed starts at 0. Only reports read it.
- History is unchanged. History is off by default (verified), so as_of reads absent for keys rewritten since, as today.
- A write that loses the clock race is still acked, and a read shows the winner. This is true today.
- Cloud copy timing (stage 2b, if Tom agrees). A peer sees an acked write after the lane stores it on the origin device, not at the ack. A crash then loses the write in both places.
- Above the soft mark the ack waits for the lane. The caller sees an ack time near the lane rate (about 140 ms each, derived) and no HTTP 503 PersistQueueFull, until the wait bound ends. [B4]
- Change feed. A sibling key gets its own event after its sibling write, not at the origin ack. [B14]
- Synchronous requests keep their meaning. They use the current path, and Durable names every key. [B15]

## Read after ack

Origin key: yes. The ack comes after the atom and the tip are in the graph as dirty records. Both writes happen in one section under the slot lock. A point read, a range list and a count on the origin hash see the write. The publish payload for the origin key equals the payload of today except for pending_replaced_tips and the header version, so the read side does not change. The purge skips dirty records, so a purge cannot drop the write before the flush. The other origin keys of the same request: yes.

The guarantee holds until the lane runs. If a higher stamp exists in the store for that key, the lane drops the write, purges the memory tip, and the read shows the winner. This is last-writer-wins, the same as a concurrent writer. The ack is not a promise against a higher stamp. The lane counts each case (lane_dropped_losers).

Sibling keys: no guarantee. The data is stale until the worker publishes it. Other devices: no promise before cloud sync.

## What a crash loses

WINDOW. The loss for the origin write has the same size as in write mode today: every acked write that the lane did not flush. The window is the lane backlog. The cap is 512 envelopes for each lane (LASTDB_RESIDENT_MAX_DEFERRED). At the measured drain of about 7 each second, 512 envelopes take about 73 s (derived). With a soft mark of 256 the window is about 37 s. A graceful stop drains the lanes first (fold_db/lifecycle.rs:224-258, wait_for_quiescent), so only a kill, a crash or a power loss loses the backlog.

DIVERGENCE TODAY, WIDER AFTER THE CHANGE (A1, verified). The capture worker appends the log entry without a wait for the lane. The entry has the bodies inline. The steady-state download skips this device's own entries. So after a crash, the cloud and the peers hold a write that the origin lost, and the origin never gets it back. Only a restore or bootstrap replays own entries. The blind ack fills the backlog sooner, so the window grows. With stage 2b the log follows the store. A crash then loses the write in both places, and the sides agree. If Tom says no to stage 2b, this class stays, and the age bound (decision 14) is the only limit.

BLIND ACK AND THE BACKLOG. Without the throttle, a serial client at 12 ms per call fills the cap of 512 in about 7 s (512 / (80 - 7), derived). Then PersistQueueFull maps to HTTP 503. The soft-mark throttle keeps the backlog below 256 and turns the 503 into a wait. [B4]

SIBLINGS. A sibling request in the queue, and a sibling envelope that the lane did not flush, are lost at a crash. The sibling is then stale on this device. Peers have it, because they build it from the origin envelope. The next write to the origin key repairs it, and so does a client retry. Tom accepts this. No orphan record results. The protein, molprot and mref records are written at bind time, not by the sibling write.

CLOCK. The author clock high-water is durable before the lane writes the data (the barrier), so a restart never reuses a counter.

## Pros

- The ack path has no store read for a plain write on a plain schema. This removes the measured 107-328 ms of sibling reads and the cold restore.
- The gate holds only memory work. The long gate hold from the durable barrier read under the locks goes away.
- Correctness at rest does not move. The durable compare in the lane (items.rs:14-70) already decides the winner for every tip, origin or sibling.
- Each stage ships alone and reverts alone. A request that fails the blind test takes the current path as a whole, so CAS, imports, replay, org, synchronous and mixed requests do not change.
- The sibling work is batched: one directory pair, one lock pass and one envelope for each drain and each lane. Today it is a serial chain for each write.
- No sibling work vanishes under load. A full queue sends the request to the current path, and the worker never drops a request.
- A protein fold error no longer fails the user write.
- The mutation log stays origin only, in ack order. With stage 2b the log never runs ahead of the store, so a crash cannot leave the origin behind its own cloud copy.
- The design closes four existing holes on the way: the random tie in one request, the memory/disk split on the same atom, the key metadata of a loser, and the slot ticket race.
- The two skeptics checked every claim against the code. 24 of 26 problems led to a concrete change; each change names a file.

## Cons

- The lane stays the limit. The lane writes the envelopes of one batch one after the other (lane_writer.rs:41-82, verified), so the drain stays at about 7 each second for each schema (MEASURED). A fast ack lets a serial client fill the cap of 512 in about 7 s (DERIVED), then HTTP 503. The throttle fixes the 503 and makes the client wait at the lane rate. ## Decisions for Tom

- 1. Log follows store (stage 2b). Today the cloud log can hold a write that a crash dropped locally, and the origin never gets it back. Fix: the capture job waits for the origin lane envelope, in queue order. Cost: the cloud copy lags by the lane lag, and the capture queue depends on lane depth. Other option: re-apply own log tail at boot, which needs a durable frontier that does not exist. Recommend: yes. If no, the class stays and stage 3 can still ship.
- 2. One merge rule for the same atom (stage 2a). Compare the full key first, and replace the whole entry on a higher key, at every memory setter and merge. The lane and physical replay already do this. No flag. No bar sees it. Recommend: yes. It is a hard gate for stage 3.
- 3. Clock catch-up. (a) The lane loser feeds the winner stamp to the clock. (b) The graph keeps the highest loaded stamp and prepare folds it in. (c) A physical snapshot restore feeds the snapshot's highest stamp. Recommend: yes for (a) and (b) in stage 2c; (c) as a separate card.
- 4. Ack throttle. Soft mark of 256 entries for each lane (half the cap), wait bound and then the current 503. A lower mark shrinks the crash window (256 / 7 is about 37 s; 128 is about 18 s) and slows bursts. Or leave the 503. Recommend: 256 with a wait, and report the mark in status.
- 5. Own counter for each mutation, and receipt.revision = last counter of the batch. This makes the later mutation of one request win on every device. Recommend: yes.
- 6. Memory compare in the gate. You said conflicts do not matter. I keep one memory compare (the shell seed): one map lookup for each key. It keeps memory equal to disk and peers when two writers meet. Recommend: keep.
- 7. Sibling envelope. (a) A worker with an immediate memory publish and one coalesced sibling_only job on the origin lane (recommended). (b) A lane of its own. (c) The first step of the origin envelope, which delays sibling memory visibility by the lane backlog.
- 8. Sibling queue full. (a) The request takes the current path with siblings inline (recommended: nothing is lost). (b) The ack waits for a permit. (c) Drop and count: this is stale forever until the next write, not a crash loss.
- 9. Delete siblings. Keep the current inline expansion until stage 6 (recommended), or accept a stale sibling after a delete now.
- 10. Record-envelope schemas and aggregates. Keep the read-modify-write for record-envelope schemas for now (recommended).
