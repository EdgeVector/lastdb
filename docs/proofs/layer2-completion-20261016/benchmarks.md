# Layer 2 before and after measurements

Date: 16 October 2026, local time. Raw timestamps use UTC.

The earlier 08409 physical batch changes reduce large-batch time, file opens, and map output.
One-key reads become slower. Some small-call medians or p95 values also increase.
Later product calls find a 256-write read-budget refusal. Final candidate measurements remain pending.

## Scope and provenance

The baseline uses `ca287339` plus inherited compile repair `9cbe67f5`.
The earlier physical commands below use `08409a220e57364052d2eca030eafd12006e6bc4`.
The final candidate changes its physical command hash, so its physical matrices require a new run.

The [provenance record](benchmark-provenance.json) records the hardware, modes, and limits.
The [command recipe](benchmark-recipe.md) defines the exact requests and generated bytes.

These are generated-home measurements, not measurements of the primary or its installed program.
The baseline is an earlier native implementation, not the legacy file format.
Both physical programs use separate fresh homes, fanout 1, and an unset disk cap.
No primary data, primary copy, archive, schema service, or cloud participates.
Other agents stop their owned nodes and product builds during each timed interval.
Ordinary host activity continues. The primary remains unchanged.

Each physical time uses the command's internal clock before its final output print.
The operating system cache state remains unknown.
A fresh process does not establish a physical cold-device read.
File bytes and calls measure instrumented userspace work, not device traffic.
The p95 uses the nearest rank; these samples do not establish a production tail guarantee.

## Generated workload

Each physical home starts with 4096 explicit keys in `Layer2Receipt`.
Each key contains `generated`, a NUL separator, and `record-N` with six decimal digits.
Bodies contain distinct SHA-256 byte chunks for each record and chunk.
Updates contain distinct chunks for each repeat, slot, and chunk.
The physical bodies use no repeated text.
Every 997th initial body is empty. Every 251st key is a tombstone.

Body sizes are 128, 1024, and 16384 bytes.
Read shapes use contiguous keys, scattered keys, duplicate keys with absence, and one bounded range page.
Write shapes use distinct keys or one repeated key within a complete batch.
Batches contain 1, 16, 64, or 256 supplied operations.
Rates count supplied keys or writes, including absent read slots and repeated writes.
The 1 KiB matrix uses 31 alternating rounds per program; the other sizes use 11 rounds.

Returned bytes, absent slots, range order, and complete operation counts match the generated input.
Normal reopen reads verify all known keys after each write case.
The 16 KiB proof uses 1024-key verification calls within its normal read budget.
Independent baseline and candidate verification calls run in parallel after the timed work.

## Intermediate b47 node result and 256-write refusal

The b47 node read phase passes all full-response checks.
Repeated identical exact-key calls use zero file I/O for batches 1, 16, 64, and 256.
Their medians are 0.247, 0.794, 2.695, and 10.615 ms, with 21 samples each.
Range 256 remains a normal fetch: median 65.427 ms, p95 66.966 ms, 34 opens, and 1078 read calls.
The captured old range median is 52.531 ms. The two programs use separate measurement windows and different native geometry.

The durable 64-write call takes 7589.598 ms, with one sample.
Its receipt reports 28.747 ms preparation and 6961.206 ms ack time; gate and publish values are zero.
The native frontier changes from 74 to 77; the generation changes from 152 to 158.
The frontier includes the clock, data, and change feed. It does not measure data publication alone.
HTTP write file-open and file-barrier counts are unavailable.

The planned durable 256-write call returns HTTP 503 `read_resource_limit`, with `retryable: false`.
The writer log names the atom live-reference count load before the transition.
The node stops normally with exit 0. No 256 latency sample exists.
One normal reopen returns all 320 exact post-64 values; the refused 256 call changes none of those values.
That node also stops with exit 0. Its generated home remains intact for review.

This product refusal blocks final completion until the targeted fix and its product proof pass.

The later ef1f run also refuses its first 256 update at the 10000-key internal read limit.
Its [typed refusal](node-ef1f-refusal.txt) and [numeric stages](node-ef1f-budget-stages.txt) preserve the actual product result.
The separate 2098 debug profile uses only five 64-record seed batches, one 64 update, and the first 256 update.
That [diagnostic profile](node-2098-refusal-inputs.json) still reaches the key limit; its timings stay outside the headline results.
